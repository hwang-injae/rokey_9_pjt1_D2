## 왜 바꾸는가
두산 파이썬 API(`DSR_ROBOT2`)는 **혼자 위에서 아래로 도는 스크립트**를 전제로 만들어졌다. 로봇 명령마다 자기가 실행기를 돌려 응답을 기다린다. 서비스 콜백 안에서 쓰면 교착하고(TS-01 B), 우회해도 "두 번째 호출부터 멈춤"(TS-01 B′), 프로세스를 나누면 "겹친 명령을 조용히 덮어씀"(TS-01 §7) 같은 함정이 남는다. 코드가 아직 없는 지금 구조를 바꾸는 것이 가장 싸다.

## 비교한 구조 (9/18 저녁, Virtual + 실제 `dsr_controller2`)
| 구조 | 결과 | 판단 |
|---|---|---|
| ① 기능 노드 3개(프로세스 3개) + 각자 DSR 전용 노드 | 번갈아 9회·연속 3회 성공. **다른 프로세스의 명령이 겹치면 드라이버가 덮어쓰고 양쪽 다 성공 응답** | 위험 남음 |
| ② 로봇 서버 노드 1개 | 시험 안 함 | 새 인터페이스·작업량 큼 |
| ③ 한 프로세스에 기능 노드 3개 + DSR 전용 노드 공유 | 번갈아 9회 성공, 겹친 요청은 `BUSY` 거절 | 절충안 |
| **④ 스크립트형: 기능은 함수, 메인 스레드가 차례로 실행, 통신 노드만 백그라운드** | **연속 6회 성공, 모션 중 상태 2.000 Hz, stop 수락** | **채택** |
| 두산의 클래스 API(`CDsrRobot`) | 같은 대기 방식 + 우리 설치본은 서비스 이름이 달라 스크립트에서도 무한 대기 | 해당 없음 |

④를 고른 이유: 문제가 생길 자리가 없다(두산이 의도한 사용법) · 강사 배포 예제 5개가 모두 이 방식 · 검증된 코드의 비율이 가장 높다 · 우리 시연에 필요한 것(시나리오·HMI·기록·역할 분담)을 잃지 않는다.
