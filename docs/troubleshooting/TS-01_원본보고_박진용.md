## 결함 A — `cobot_common`에 두산 API 초기화 진입점이 없다

### 현재 문서 상태
- SDD §3.1 `cobot_common` 함수표에는 `move_to` `move_rel` `grip` `grip_level` `release` `weigh` `force_on/off` `contact_down` `periodic_search` `safe_retreat` **11개만** 있고 초기화 함수가 없다.
- `DR_init`은 문서 전체에서 **환경설정의 PYTHONPATH 함정**(`No module named 'DR_init'`) 맥락으로만 등장한다. **코드에서 `DR_init.__dsr__node`를 세팅해야 한다는 서술이 어디에도 없다.**

### 원인
설치된 `DSR_ROBOT2.py`는 **import되는 순간** 아래를 실행한다(`~/ws_cobot_pjt/ws_dsr/src/doosan-robot2/dsr_common2/imp/DSR_ROBOT2.py:39`).

```python
g_node = DR_init.__dsr__node          # import 시점에 한 번 읽고 고정
_ros2_set_robot_mode = g_node.create_client(...)   # g_node 가 None 이면 여기서 터짐
```

즉 **`DR_init.__dsr__node = <실제 노드>` 를 먼저 하고, 그 다음에 `DSR_ROBOT2` 를 import해야 한다.** 함수표에 초기화 함수가 없으면 `robot.py`는 자연히 파일 상단에 `from DSR_ROBOT2 import movej, ...` 를 쓰게 되고, 기능 노드가 `import cobot_common` 하는 시점(= `rclpy.init()` 전, 노드 생성 전)에 그대로 터진다.

### 재현
```python
import rclpy, DR_init
rclpy.init()
node = rclpy.create_node('t', namespace='dsr01')
DR_init.__dsr__id = 'dsr01'; DR_init.__dsr__model = 'm0609'
# DR_init.__dsr__node 를 세팅하지 않은 채 import
from DSR_ROBOT2 import movej
```
**실측 결과**
```
AttributeError: 'NoneType' object has no attribute 'create_client'
```

### 수정안
`cobot_common`에 초기화 함수를 추가하고, 기능 노드는 `__init__`에서 한 번 호출한다.

```python
# src/cobot_common/cobot_common/bootstrap.py
import DR_init

_dsr = None

def init(node, robot_id='dsr01', robot_model='m0609'):
    """기능 노드의 __init__ 맨 앞에서 한 번 호출."""
    global _dsr
    DR_init.__dsr__id = robot_id
    DR_init.__dsr__model = robot_model
    DR_init.__dsr__node = node        # ← 반드시 import 보다 먼저
    import DSR_ROBOT2 as _m
    _dsr = _m
```
**검증 완료**: 위 순서로 하면 `movej` `movel` `task_compliance_ctrl` `set_desired_force` `move_spiral` `check_force_condition` 전부 정상 로드됨을 확인했다. 두산 공식 예제(`dsr_example2/.../single_robot_simple.py`)도 동일한 순서를 쓴다.

## 결함 B — 기능 노드의 실행기 구조가 명시돼 있지 않다 (V-21 실측)

### 현재 문서 상태
- SDD §9.2 **V-21**에 "서비스 콜백 안 장시간 모션 … 막히지 않는가(콜백 그룹·MultiThreadedExecutor)"가 **검증 예정 항목**으로만 있다(담당 민범진, 9/19 오전).
- 기능 노드의 `main()` 구조·실행기·콜백 그룹에 대한 **설계 서술은 §5.2~5.4 어디에도 없다.** 명시가 없으면 표준대로 `rclpy.spin(node)`를 쓰게 된다.

### 원인
`f1_node`·`f2_node`·`f3_node`는 전부 **자기 서비스 콜백 안에서 로봇을 움직인다**(`/f1/pick`, `/f2/weigh`, `/f3/wipe_bowl` …). 그런데 `DSR_ROBOT2`의 모든 로봇 명령은 내부적으로 아래 패턴이다.

```python
future = _ros2_move_joint.call_async(req)
rclpy.spin_until_future_complete(g_node, future)   # executor= 인자 없음 → 전역 실행기 사용
```

기본 `rclpy.spin(node)` + 기본 콜백 그룹(`MutuallyExclusiveCallbackGroup`) 조합에서는
**현재 실행 중인 서비스 콜백이 그룹을 점유한 채 응답을 기다리고, 그 응답을 처리할 콜백은 같은 그룹이라 실행 순서를 얻지 못한다** → 교착.
`DSR_ROBOT2`는 대부분의 호출에 타임아웃을 주지 않으므로 **무한 대기**가 된다.

> AGENTS.md §5 환경 함정의 "노드가 멈춰 Ctrl+C를 누르면 `dsr_controller2`가 그 요청 안에 갇혀 이후 모든 실행이 첫 호출부터 멈춘다"는 증상과 일치한다.

### 재현 (3단계, 로봇 없이)

| 구성 | 결과 |
|---|---|
| ① 서비스 콜백 안에서 같은 노드로 `spin_until_future_complete` | `RuntimeError: Executor is already spinning` (즉시 크래시) |
| ② DSR용 노드를 별도로 분리 | **여전히 실패** — `executor=` 를 안 넘기면 프로세스 전역 실행기를 공유하므로. 크래시 대신 응답을 영영 못 받고 타임아웃 |
| ③ `MultiThreadedExecutor` + `ReentrantCallbackGroup` | ✅ **성공** |

③의 재현은 실제 구조(`flow_node` → `f3_node` → `dsr_controller2` 3개 별도 노드)를 그대로 흉내 내어 확인했다.
```
>>> f3_node: /wipe_bowl_sim 콜백 시작
>>> dsr_controller_sim: movej 실행 흉내
>>> f3_node: dsr 호출 완료, done= True
=== 최종 결과 === done= True result= wipe_bowl done
```

### 수정안
`cobot_common`이 `spin` 헬퍼를 제공하고, 기능 노드는 `rclpy.spin()` 대신 이것을 쓴다.
추가로 `init()`이 노드의 **기본 콜백 그룹 자체를** 교체하면, 각 노드가 `create_service(..., callback_group=...)`를 매번 신경 쓰지 않아도 되고 `DSR_ROBOT2`가 내부에서 만드는 클라이언트까지 함께 안전해진다(이 방식도 실측으로 동작 확인).

```python
# bootstrap.py (결함 A의 init 에 한 줄 추가)
from rclpy.callback_groups import ReentrantCallbackGroup
from rclpy.executors import MultiThreadedExecutor

def init(node, robot_id='dsr01', robot_model='m0609'):
    ...
    node._default_callback_group = ReentrantCallbackGroup()   # ← 추가

def spin(node):
    """main()에서 rclpy.spin(node) 대신 사용."""
    executor = MultiThreadedExecutor()
    executor.add_node(node)
    try:
        executor.spin()
    finally:
        executor.shutdown()
```

기능 노드 쪽은 두 줄만 바뀐다.
```python
class F3Node(Node):
    def __init__(self):
        super().__init__('f3_node')
        cobot_common.init(self)        # ← 추가

def main(args=None):
    rclpy.init(args=args)
    node = F3Node()
    try:
        cobot_common.spin(node)        # ← rclpy.spin(node) 대신
    finally:
        node.destroy_node(); rclpy.shutdown()
```

## D(참고) `check_force_condition` 반환값 — 매뉴얼과 실제가 다름

접촉 동작(`contact_down`·안착·닦기) 판정이 전부 이 함수 위에 있으므로 **가장 위험한 함정**이다.

| 출처 | 반환값 |
|---|---|
| DRL 프로그래밍 매뉴얼(v2-manual) | `True` / `False` |
| **실제 `DSR_ROBOT2.py:5478`** | **조건 만족 `0` / 실패 `-1`** |

파이썬에서 `0`은 거짓이므로 `if check_force_condition(...):` 로 쓰면 **판정이 정반대로 뒤집힌다**(힘이 안 걸렸는데 "접촉했다"로 처리). 반드시 `== 0` 으로 비교하거나, `cobot_common`에서 `bool`로 감싸 제공한다.

```python
# DSR_ROBOT2.py 5478~ (실제 코드)
ret = 0 if (result.success == True) else -1
return ret
```

참고로 `check_position_condition` 도 동일하다. 또한 `~/ws_cobot_pjt/ws_dsr/src/rokey/rokey/hw_gear_move.py:106,114`(기어 과제 코드)에 이 비교가 빠져 있어 로직이 뒤집힌 상태다.

## 검증 환경과 한계

- ROS 2 Jazzy / Python 3.12, `~/ws_cobot_pjt/ws_dsr` 설치본의 `DSR_ROBOT2.py`(11,743줄) 직접 확인
