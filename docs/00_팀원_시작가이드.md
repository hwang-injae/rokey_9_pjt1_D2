## 0-1. git·GitHub 5분 개념 (처음이면 꼭 읽기)

**git** = 내 PC에 깔린 "파일 변경 기록 프로그램". **GitHub** = 그 기록을 팀이 공유하는 웹사이트. 둘은 다르다. 터미널 명령 `git …`은 내 PC의 git에게 하는 말이고, GitHub 웹 화면은 팀 공용 창고를 보는 곳이다.

| 용어 | 한 줄 뜻 | 비유 |
|---|---|---|
| 저장소 (repository) | 프로젝트 폴더 전체 + 변경 기록 | 팀 공용 창고. GitHub에 1개(원격), 각자 PC에 복사본 1개(로컬) |
| clone | GitHub 저장소를 내 PC로 복사 | 창고를 통째로 내 방에 복사 |
| 커밋 (commit) | "지금 상태"를 이름 붙여 저장 | 게임 세이브. 메시지가 세이브 이름 |
| push | 내 PC의 커밋을 GitHub로 올림 | 내 세이브를 창고에 올림 |
| pull / fetch | GitHub의 최신 커밋을 내 PC로 받음 | 남이 올린 세이브를 내 방으로 가져옴 (fetch는 가져만 오고, pull은 가져와서 합침) |
| 브랜치 (branch) | 작업 갈래. `main`은 정본, 나머지는 각자 작업용 | 정본 원고(main)는 건드리지 않고 복사본(내 브랜치)에 쓴다 |
| PR (Pull Request) | "내 브랜치를 main에 합쳐 주세요" 요청 | 복사본을 정본에 반영해 달라는 결재 |
| 리뷰 / 승인 (approve) | 팀원이 PR을 보고 OK | 결재 도장 |
| merge | 승인된 PR을 main에 합침 | 정본에 반영 |
| 충돌 (conflict) | 두 사람이 같은 줄을 다르게 고침 | 둘 중 무엇을 남길지 사람이 정해야 함 |

**한 사이클**: `main 최신 받기 → 내 브랜치 만들기 → 코드 고치기 → 커밋 → push → GitHub에서 PR → 팀원 승인 → merge`. 이걸 작업(taskID)마다 반복한다.

**하면 안 되는 것 3개**: ① `main`에서 직접 작업·push ② 남의 브랜치 삭제 ③ `build/ install/ log/`·영상·토큰을 커밋.

### 터미널 기본 (이것만)
```bash
pwd                 # 지금 내가 있는 폴더 경로
ls                  # 이 폴더 안 목록 (ls -a 는 숨김 파일까지)
cd 폴더이름          # 그 폴더로 들어감.  cd ..  는 한 단계 위,  cd ~  는 홈
```
프롬프트 `injae@pc:~/rokey9_pjt1/rokey_pjt01_ws$` 에서 `~/rokey9_pjt1/rokey_pjt01_ws` 가 "지금 있는 폴더"다. **git 명령은 항상 저장소 폴더 안에서** 친다. 모르겠으면 `cd $REWASH_WS` 부터.

### GitHub 웹 화면 어디에 뭐가 있나
저장소 주소 `https://github.com/hwang-injae/rokey_9_pjt1_D2` 를 열면:
- 상단 탭 **Code**: 파일 목록. 왼쪽 위 `main ▾` 버튼이 **브랜치 선택** — 여기서 내 브랜치를 고르면 그 브랜치의 파일이 보인다
- 상단 탭 **Issues**: 작업·버그·인터페이스 변경 요청 (초록 **New issue** → 템플릿 3종)
- 상단 탭 **Pull requests**: 올라온 PR 목록. 초록 **New pull request** 로 새로 만들 수도 있지만, push 직후 뜨는 노란 **Compare & pull request** 배너를 누르는 게 쉽다
- 파일을 클릭하면 내용 보기, 연필 아이콘은 웹에서 직접 수정(문서 한 줄 고칠 때만. 이때도 "Create a new branch … and start a pull request" 를 선택)

### 1-2. 토큰 만들기 (비밀번호 대신 쓴다)
GitHub는 push할 때 계정 비밀번호를 받지 않는다. **개인 토큰(Personal Access Token)** 을 비밀번호 자리에 넣는다.

1. 주소창에 `https://github.com/settings/tokens` 입력 (계정 Settings → Developer settings → Personal access tokens → Tokens (classic))
2. **Generate new token → Generate new token (classic)**
3. Note: `rokey_pjt1` / Expiration: **30 days** 이상(10월 초까지) / 권한: **`repo`** 하나만 체크
4. **Generate token** → `ghp_`로 시작하는 문자열이 한 번만 보인다. **바로 복사**해 안전한 곳(메모장 등, 채팅 금지)에 둔다.

### 1-3. git 설정 (내 PC, 한 번)

| 비전·카메라 제안 | `비전 불가. 파지 폭·하중·힘·위치로.` |

## ④-2. 실습: 첫 PR을 끝까지 한 번 (15분, 문서 한 줄로)

이 연습을 마치면 매일 흐름(⑤)이 전부 이해된다. 예시 이름은 본인 것으로 바꾼다.

**1) 최신 main에서 시작**
```bash
cd $REWASH_WS
git checkout main && git pull origin main
```
> 기대 출력: `Already up to date.` 또는 받은 파일 목록

**2) 연습 브랜치 만들기**
```bash
git checkout -b seokhyung/20260918-ENV-01-first-pr
```
> 기대 출력: `Switched to a new branch 'seokhyung/20260918-ENV-01-first-pr'`

**3) 파일 한 줄 고치기** — `docs/test_logs/` 폴더에 내 환경 완료 기록을 만든다
```bash
mkdir -p docs/test_logs
echo "# ENV-01 환경 점검 완료 — 한석형 2026-09-18 (sodvir·cbc 성공)" > docs/test_logs/20260918_ENV-01_한석형.md
git status
```
> `Untracked files: docs/test_logs/...` 가 보이면 정상

**4) 커밋**
```bash
git add docs/test_logs/20260918_ENV-01_한석형.md
git commit -m "docs(setup): ENV-01 환경 점검 완료 기록 (한석형)"
```
> 기대 출력: `1 file changed, 1 insertion(+)`. 처음이면 user.name/email 설정하라는 메시지가 뜰 수 있다 → 1-3 참조

**5) push**
```bash
git push -u origin seokhyung/20260918-ENV-01-first-pr
```
> 처음이면 Username(내 GitHub ID)과 Password(**토큰**)를 묻는다. 성공하면 마지막에
> `remote: Create a pull request for '...' on GitHub by visiting: https://github.com/.../pull/new/...` 링크가 뜬다

**6) GitHub에서 PR 만들기**
1. 위 링크를 브라우저에 붙여넣거나, 저장소 페이지 상단의 노란 배너 **Compare & pull request** 클릭
2. 위쪽 `base: main ← compare: seokhyung/...` 가 맞는지 확인
3. 제목: `docs(setup): ENV-01 환경 점검 완료 기록 (한석형)`
4. 본문 템플릿에서 "실기 영향" 칸의 **"실기(Real) 동작에 영향 없음"** 체크
5. 오른쪽 **Reviewers** 톱니 → **hwang-injae** 클릭 (승인은 황인재만 할 수 있다. 에이전트가 먼저 규칙·main 병합·통합 테스트를 검토하고 코멘트를 남긴다)
6. 초록 **Create pull request**

**7) 승인** (황인재)
에이전트가 PR을 검토해 코멘트를 남기면 황인재가 PR 열기 → **Files changed** → **Review changes** → **Approve** → **Submit review**. 거절이면 **Request changes**에 이유가 적힌다 → 고쳐서 같은 브랜치에 push하면 PR이 자동 갱신된다

**8) merge**
PR 페이지 아래 초록 **Squash and merge** → **Confirm squash and merge**. 그 뒤 나오는 **Delete branch** 는 **누르지 않는다**(팀장 승인 후 삭제).

**9) 내 PC를 최신으로**
```bash
git checkout main && git pull origin main
git log --oneline -3        # 내 커밋이 main에 들어와 있으면 성공
```

여기까지 되면 GitHub 사용법은 끝난 것이다. 이후는 파일이 코드로 바뀔 뿐 똑같다.

## ⑤ 매일 작업 흐름 (git)

### 5-1. 아침: 최신 main 받기
```bash
cd $REWASH_WS
git fetch origin
git checkout main
git pull origin main
```

### 5-2. 내 브랜치 만들기 — 작업(taskID)마다 하나
taskID는 **구글 드라이브 일정표**의 맨 오른쪽 ID 열(`F1-02`, `INT-13` …). 이름은 전부 영문 소문자·하이픈.
```bash
git checkout -b seokhyung/20260919-F1-02-pick-search      # {이름}/{YYYYMMDD}-{taskID}-{설명}
git branch                                                 # * 표시가 내 브랜치인지 확인
```

### 5-3. 작업 → 단위기능 테스트 → 녹화
- 에이전트와 STEP 진행. 완성되면 **단위기능 테스트**(기준: `docs/03_설계_SDD.md` §9.3의 내 TC).
- 테스트는 **녹화**한다: `YYYYMMDD_TCxx_기능_담당_시도N.mp4` (예 `20260920_TC01_pick_한석형_시도1.mp4`). 영상은 드라이브에 올리고 링크를 `docs/test_logs/YYYYMMDD_TCxx.md`에 적는다.

### 5-4. 저장(commit)하고 올리기(push) — 하루 1회 이상
```bash
git status                                  # 바뀐 파일 확인. build/ install/ log/ 가 보이면 안 됨
git add src/f1_handling/f1_node.py src/f1_handling/config/f1.yaml     # 바꾼 파일만 (git add . 지양)
git commit -m "feat(f1): pick 탐색 파지 — 접촉 하강·폭 판정·재탐색"     # <타입>(<스코프>): <제목>
git push -u origin seokhyung/20260919-F1-02-pick-search              # 처음 한 번 -u, 이후 git push
```
타입은 10개만: `feat fix refactor style docs test chore remove perf ci`. 스코프: `f1 f2 flow f3 f4 common msgs cell bringup docs setup`.

### 5-5. 통합 전: 최신 main을 내 브랜치에 합치기
```bash
git fetch origin
git merge origin/main            # 충돌 나면 5-8
cbc                              # 다시 빌드·통합 테스트
```

### 5-6. PR 올리기 (GitHub 화면)
1. push 직후 터미널에 뜨는 링크를 열거나, 저장소 페이지의 **Compare & pull request** 클릭
2. 제목: 커밋 규칙과 같은 형식 `feat(f1): pick 탐색 파지`
3. 본문 템플릿이 자동으로 뜬다. **"실기 영향" 칸과 단위 테스트 영상 파일명**을 채운다
4. 오른쪽 **Reviewers**에 **hwang-injae** 지정 → **Create pull request**
5. 승인이 오면 **Squash and merge** 버튼 → Confirm
6. 브랜치 삭제는 **팀장(한석형) 승인 후에만**. "Delete branch" 버튼을 바로 누르지 않는다.

### 5-7. PR이 거절(Request changes)되면
코멘트에 적힌 항목(예: main 병합 안 됨, 영상 파일명 없음, 숫자 하드코딩)을 고친 뒤 **같은 브랜치**에 커밋·push하면 PR이 자동으로 갱신된다. 새 PR을 만들지 않는다. 다른 팀원 PR에 코멘트는 자유롭게 달아도 되지만 승인 버튼은 황인재만 누른다.

### 5-8. 자주 나는 문제
| 증상 | 원인 | 해결 |
|---|---|---|
| `Password for ...` 에서 실패 | 계정 비밀번호를 넣음 | 1-2 토큰을 넣는다. 저장된 잘못된 값은 `rm ~/.git-credentials` 후 다시 |
| `! [rejected] ... (fetch first)` | 원격이 더 최신 | `git pull origin 내브랜치` 후 다시 push |
| `Need to specify how to reconcile divergent branches` | pull 방식 미설정 | `git config --global pull.rebase false` 후 다시 |
| `CONFLICT (content)` | 같은 줄을 두 명이 고침 | 파일을 열어 `<<<<<<<` `=======` `>>>>>>>` 사이에서 맞는 쪽을 남기고 표시 삭제 → `git add 파일` → `git commit`. 모르겠으면 그 상태로 팀 채널에 |
| 실수로 `main`에서 작업함 | 브랜치 안 만듦 | `git stash` → `git checkout -b 이름/날짜-ID-설명` → `git stash pop` |
| `build/`가 커밋에 들어감 | `git add .` | `git rm -r --cached build install log` → commit. `.gitignore`가 막아주니 원래는 안 들어간다 |
| 다른 팀원 노드가 안 보임 | DOMAIN·네트워크 | 양쪽 `ROS_DOMAIN_ID=60`, 같은 스위치. 환경설정 문서 10-5 |

## 부록 A. 명령 사전 (뜻 · 언제)
| 명령 | 뜻 | 언제 |
|---|---|---|
| `git status` | 지금 브랜치·바뀐 파일 보기 | 뭘 하기 전마다 |
| `git fetch origin` | GitHub 최신 정보만 받기 (내 파일 안 바뀜) | 아침, 통합 전 |
| `git pull origin main` | main 최신을 받아 합치기 | 아침 (main에서) |
| `git checkout main` | main 브랜치로 이동 | 새 작업 시작 전 |
| `git checkout -b 이름/날짜-ID-설명` | 새 브랜치 만들고 이동 | 작업(taskID)마다 |
| `git branch` | 브랜치 목록, `*`가 현재 | 헷갈릴 때 |
| `git add 파일` | 이 파일을 다음 커밋에 포함 | 커밋 전 |
| `git commit -m "타입(스코프): 제목"` | 저장 | add 후 |
| `git push -u origin 브랜치` / `git push` | GitHub로 올리기 | 하루 1회 이상 |
| `git merge origin/main` | main 최신을 내 브랜치에 합치기 | 통합 테스트 전 |
| `git log --oneline -5` | 최근 커밋 5개 | 확인용 |
| `git diff` | 아직 커밋 안 한 변경 내용 | 뭘 고쳤는지 볼 때 |
| `git stash` / `git stash pop` | 변경을 잠시 치웠다가 되살림 | main에서 실수로 작업했을 때 |
| `git restore 파일` | 파일 변경 취소 (되돌리기) | 잘못 고쳤을 때 (주의: 복구 불가) |
